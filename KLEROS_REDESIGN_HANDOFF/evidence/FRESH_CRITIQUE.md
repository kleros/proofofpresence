# Kleros redesign — fresh independent critique

**Review date:** 28 October 2026  
**Scope:** Read-only review of `DESIGN_EVIDENCE.md`, `source_events_inventory.md` and `source_finance_inventory.md`; no prior chats, repositories, browser sessions or transactions were consulted or exercised by this reviewer.  
**Purpose:** Decision support for the already active implementation, including a rebuild if it serves the authorized brief.

## Three-sentence verdict

**OBSERVED (BROWSER/SOURCE, as recorded in the evidence packet):** Kleros has an established public event discovery surface and substantial source-defined financial safeguards, while an integrated multi-event financial journey is not established by the inspected surfaces. **ESTIMATE:** The redesign should make event identity, admission, deposit progress, financial eligibility, unresolved cases and the next permitted action unambiguous, with a common visual system reinforcing those distinctions. **ESTIMATE:** Concentrate design decisions in the four areas below, preserve the product rules, and treat mobile, authenticated and asynchronous transaction behavior as validation work still required.

## What already works

- **OBSERVED (BROWSER):** The Events directory exposes All/Upcoming/Past, List/Calendar, search, topic and event-type controls; event detail presents date, local time/timezone, venue, an RSVP route and calendar action. These provide a useful starting point for discovery and event identity. [E: B1–B2]
- **OBSERVED (BROWSER):** The disconnected commitment page makes the network, ETH-only requirement, exact deposit amount, contract address and numbered prerequisites visible. **OBSERVED (SOURCE):** Existing code distinguishes pending receipts, previous deposits, admission, matched cases, reserved shares, failed-transfer claims and no-list recovery. These are valuable behaviors and domain distinctions to carry into the new journey. [E: B3; F: §2]
- **OBSERVED (SOURCE):** The owner console identifies LIVE, REHEARSAL and LOCAL TEST CHAIN, separates owner actions from actions available to any wallet, and simulates transactions before wallet submission. Rehearsal can involve real ETH. [F: §3]
- **OBSERVED (CALCULATED):** All six supplied text pairs pass normal-text AA; the white-on-purple console button is a narrow pass at 4.5053:1. The inspected Events typography, tokens and original SVG assets offer a concrete visual precedent, without establishing an official universal brand standard or full accessibility conformance. [E: §3–4]

## Five decisions that must survive

1. **Preserve financial and deployment semantics.** The current v7 ETH/V1 behavior, compatibility with old deployments and isolation between events are constraints on every concept. Changing navigation, styling or product foundations must not silently change which contract, version, chain or event an action addresses. [E: §0, §3]
2. **Keep admission and evidence independent.** A deposit is not host approval; self-declared “I was there” and booth activity are not financial attendance authorization; public event metadata does not establish a guest-to-wallet identity. Editorial access and staff access must not silently confer settlement authority. [E: §0; S: Cards and event detail, Administration and financial integration gap; F: §4]
3. **Represent unresolved money accurately.** Ordinary payouts may complete while matched cases retain reserved shares; final ruling and settlement are distinct; failed-transfer claims and no-list recovery have different prerequisites and meanings. Cancellation copy must respect the distinction between registered stakers and other deposits. [F: §2, §5]
4. **Preserve the free attendance route and voluntary consent.** A wallet or ETH transfer must not become an invented requirement for ordinary attendance, and marketing consent remains optional. The visible public event copy says attendance is free with host approval, while commitment is an optional separate route. [E: §0, B2, B5]
5. **Keep existing content and access usable across the migration.** Events, talks, materials, Q&A, historical links and private access need a deliberate retention or migration decision; the redesign does not authorize disclosure of private content or expansion of financial permissions. Useful discovery controls and recognizable Kleros assets can carry forward within that boundary. [E: §0; S: Layout, navigation and browsing, Cards and event detail, Interpretation and unresolved visual checks]

## Confidence and remaining gaps

### High confidence in the basis for prioritization

The supplied evidence directly records the source wording behind the payout finding, the absence of established multi-event financial navigation in Kickback, the independence of admission and financial attendance, and the fact that the Events Luma sync is not wallet/deposit reconciliation. The proposed priorities follow from those facts, but their user impact remains an estimate. The supplied contrast calculations support selected-pair passes and do not justify a color-failure finding. [E: §3–4; S: Administration and financial integration gap; F: §2, §5]

### What this review cannot establish

- **Viewport and accessibility:** All supplied public browser captures were at **1363 × 936 CSS px**. Live mobile behavior, live 1440px rendering, hover, complete keyboard/screen-reader flows, focus transitions, disabled-state contrast and transparent or gradient treatments remain unverified. A measured 40–42px control is not automatically a WCAG 2.2 AA target-size failure; a proposed 44px usability target must be identified as a design target. [E: §2, §4–5]
- **Financial behavior:** No wallet was connected and no deposit, lookup, dispute or payout was submitted. Pending, replacement/reorg, read failure, rejection, receipt and recovery behaviors require state-specific validation. Live fees are snapshots and must not be fixed as future prices. [E: B3–B4, §5; F: §5]
- **Private and organizer workflows:** No authenticated Events desk, owner-console runtime or booth staff flow was opened in the browser. Source indicates authority and capabilities; it does not prove deployed permissions, data completeness or successful execution. [E: §5; S: evidence boundary; F: evidence boundary, §3–5]
- **Data and workload:** No observed volume, error rate, participant research, task timing or conversion metric supports a density choice or a quantitative improvement claim. Import provenance is incomplete in the source handoff, and the exact current guest-to-wallet reconciliation process needs explicit specification. [E: §3; S: Administration and financial integration gap]
- **Deployment and migration:** The source snapshots and observed deployments were not proven identical. The observed custom-domain connection failure does not establish a general outage, and direct `#status` navigation succeeded, so neither should become a fabricated navigation defect. Preserve an explicit migration boundary for private content, URLs and old deployments. [E: B1, B4, §0, §5]
- **Prototype QA boundary:** The implementation handoff reports that the cloud browser blocks local `file://` prototypes. Local DOM/state checks, deterministic contrast calculations and static design renders can support preparation, while the supplied Playwright checks remain for execution in Codex's environment; none substitutes for an observed live mobile or authenticated browser pass. Exact retrieved source font files and their OFL licenses may be used for the prepared mockups. This is a preparation constraint supplied by the coordinating agent, not a new browser observation by this reviewer.
